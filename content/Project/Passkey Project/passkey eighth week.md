### Let's patch the vulnerable code!!

현재 취약점 : 구형 인증기로 위장한 가상 인증기가 aaguid를 조작한 패킷을 보내 uv flag를 우회한다. aaguid 사칭에 대응할 로직이 부재한다.


새로 추가한 코드 : 

1. 구형 인증기로 등록 시 credential에 aaguid를 추가해 저장했다가 인증할 때 DB에서 검증
	![[화면 캡처 2026-05-20 142741.png|661]]
	>credential에 aaguid도 저장한다.
	
	![[화면 캡처 2026-05-20 142813.png|661]]
	>DB에 저장된 aaguid인지 확인해야만 플래그를 우회한다.
2. 패스키 등록 시 ``attestment``의 ``fmt`` key에서 ``attStmt``(attestation statement)을 검증
	-> 가상 인증기는 내용물이 존재하지 않으므로 탈락한다.
	![[화면 캡처 2026-05-20 142852.png]]
	> 실제 인증기의 경우 root CA까지의 인증서 체인이 안에 들어 있다. 이것은 FIDO server를 활용해 검증해야 할 문제지만 이 실습에서 드러날 일이 없으므로 생략한다.


한계점 : 실습을 못한다! 왜냐면 취약점을 구현하던 당시에 구형 인증기를 구할 수 없어서 **등록(구형 인증기 역할의 가상 인증기)&인증(구형 인증기를 사칭하는 역할의 가상 인증기)** 를 사용했는데, 패치한 후에는 가상 인증기 사용이 완전히 막혀서 실제 구형 인증기는 설계한대로 우회가 가능할 지 미지수이다.
![[화면 캡처 2026-05-20 145046.png]]
>이제 가상 인증기로 수작을 부리려 해도 시작이 막힌다. 실제 구형 인증기라면 attestment도 제대로 있어야 하지만 가상 인증기는 제대로 갖춰져 있지 않기 때문이다.


소감 : LLM에게 농락 당하면서 버틴 1개월에 비해 결과가 이상한 방향으로 가버려서 너무 아쉽다. 취약점을 구현하는 것 뿐 아니라, 이 과정 자체를 뜯어서 하나하나 분석만 해봐도 굉장히 성장할 수 있을 것 같아 도전해보고자 한다.
